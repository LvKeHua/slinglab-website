## 一、项目概述

Stone Crypto 是一个加密货币交易日记/仪表盘应用，连接 Binance 和 Bybit 交易所，展示：
- 账户资产余额（实时 USDT 估值）
- 已平仓交易历史（按交易对配对买入/卖出）
- 期货持仓
- 分析图表（PnL 分布、胜率、持仓时间等）

### 架构

```
前端 (Next.js)  →  Cloudflare Worker (API)  →  Binance/Bybit API
                      ↑
                   KV 存储（缓存、设置、静态文件）
```

- **前端**: Next.js 14 (App Router)，部署为静态文件存入 Cloudflare KV
- **后端**: Cloudflare Worker (`stone-journal`)，处理所有 API 请求
- **代理**: Cloudflare Tunnel (`binance.slinglab.xyz`) → 本地 Node.js proxy (port 8765) → Clash (port 7897) → Binance API

## 四、核心问题：交易对覆盖率不足

### 问题描述

Binance 有 **480 个** USDT 现货交易对，我们当前只查询 **~35 个**。如果用户交易过不在 `knownPairs` 列表中的小币种，那些交易记录不会出现在 Dashboard 中。

### 根本原因

**Cloudflare Worker 免费版限制：每次调用最多 50 个 subrequest。**

当前每次 Dashboard 请求的 subrequest 消耗：
| 调用 | 数量 |
|------|------|
| Binance 账户查询 (`/api/v3/account`) | 1 |
| Binance myTrades (每个交易对一个) | ~35 |
| Binance 批量价格 (`/api/v3/ticker/price`) | 1 |
| Binance 期货持仓 (`/fapi/v2/positionRisk`) | 1 |
| Bybit 执行记录 (5页) | 5 |
| **总计** | **~43** |

如果要查全部 480 个交易对：1 + 480 + 1 + 1 + 5 = **488 subrequests** → 远超 50 限制。

### 解决方案对比

| 方案 | 费用 | 难度 | 效果 |
|------|------|------|------|
| **A. 升级 Workers 付费版** | $5/月 | 极低 | 在 `wrangler.toml` 加 `[limits] subrequests = 1000`，一次性查询所有交易对 |
| **B. KV 分批缓存同步** | 免费 | 中等 | 每5分钟 Cron 分批拉取（每批20个交易对），约2小时轮完一轮，存入 KV，Dashboard 直接读缓存 |
| **C. 接受当前覆盖** | 免费 | 零 | ~35 个交易对覆盖主流币种 |

**推荐方案 A**：$5/月是最简单直接的解决方案。

- **原因**: 未实现 Bybit 余额查询（`/v5/account/wallet-balance`）

## 八、Binance API 调用流程

```
Dashboard 请求
    │
    ├─ fetchBinanceTrades()
    │   ├─ fetchAccountBalances() → /api/v3/account (1 subrequest)
    │   ├─ 对 ~35 个 knownPairs 并行调用 /api/v3/myTrades (35 subrequests)
    │   └─ pairTrades() → 买入/卖出配对
    │
    ├─ fetchAccountBalancesDetailed()
    │   ├─ /api/v3/account (1 subrequest)
    │   └─ /api/v3/ticker/price (1 subrequest, 批量获取所有价格)
    │
    ├─ fetchBinanceFuturesPositions()
    │   └─ /fapi/v2/positionRisk (1 subrequest)
    │
    ├─ fetchBybitTrades()
    │   └─ 5 页 /v5/execution/list (5 subrequests)
    │
    └─ 总计 ≈ 43 subrequests ✅ (在 50 限制内)
```

所有 Binance 请求通过代理：
```
Worker → https://binance.slinglab.xyz/proxy/api/v3/...
       → Cloudflare Tunnel
       → localhost:8765 (Node.js proxy)
       → Clash (port 7897)
       → Binance API
```

## 九、交易配对逻辑

### Binance (`pairTrades`)

1. 按 `time` 排序所有交易
2. 每个 symbol 分离买入（`isBuyer=true`）和卖出（`isBuyer=false`）
3. FIFO 配对：最早的买入配最早的卖出
4. 买入先于卖出 = Long；卖出先于买入 = Short
5. 计算 `realisedPnl = (exitPrice - entryPrice) * qty - totalCommission`

### Bybit (`pairBybitTrades`)

1. 按 `execTime` 排序执行记录
2. 每个 symbol 分离 Buy 和 Sell
3. FIFO 配对
4. 计算 `realisedPnl = rawPnl - totalFee`

## 十三、Rolling Refresh 架构设计（方案 B 详细）

如果选择不升级付费版，以下是 KV 分批同步的详细设计：

### KV 键设计

| 键 | 值 | TTL |
|----|---|-----|
| `binance_symbols` | `string[]` — 所有活跃 USDT 交易对 | 24h |
| `sync_cursor` | `{ batchIndex, totalBatches, lastFullSync }` | 无 |
| `binance_trades_cache` | `ClosedTrade[]` — 所有已配对交易 | 无 |
| `bybit_trades_cache` | `ClosedTrade[]` — 所有 Bybit 交易 | 无 |

### Cron 逻辑（每 5 分钟）

```
1. 检查 binance_symbols 是否过期（>24h），过期则重新获取
2. 读取 sync_cursor → 计算当前批次 [batchIndex * 20, (batchIndex+1) * 20)
3. 对当前批次的 20 个交易对调用 /api/v3/myTrades
4. 合并新交易到 binance_trades_cache（按 trade ID 去重）
5. 获取 Bybit 执行记录（5页）→ 更新 bybit_trades_cache
6. batchIndex++，如果 >= totalBatches 则重置为 0
7. 更新 sync_cursor
```

### Dashboard 逻辑

```
1. 从 KV 读取 binance_trades_cache + bybit_trades_cache（0 subrequests）
2. 实时获取 Binance 账户余额（1 subrequest + 1 批量价格）
3. 实时获取 Binance 期货持仓（1 subrequest）
4. 合并返回
```

### 时间估算

- 480 交易对 / 20 每批 = 24 批
- 每批 5 分钟 = **约 2 小时完成一轮完整同步**
- Dashboard 响应时间：**< 3秒**（读缓存 + 少量实时 API）
