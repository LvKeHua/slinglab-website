## 一、系统定位

**一句话**：基于 @derrrrrrrq 小币永续方法论的全市场聚合筛选器——从 678 个 Binance USDT 永续合约中，识别处于**吸筹/拉升早期**的币，并**排除**所有已知的负 EV 陷阱。

**核心认知**（验证确立）：
> 换手是事件指标，不是前兆指标。前兆不在"放量"里，在"有底仓的平静"里——OI 有底仓 + 波动率压缩 + 价格缓涨 + 量能枯竭。

## 三、全市场聚合（2026-08-07 上线）

**背景**：原系统只用 Binance 单所数据。查证 @derrrrrrrq 推文发现他用全市场（"3月14号 $WLFI 在各大交易所OI翻倍"、"清算定价权在gate spot"、"空棒子现货的习惯"），因此将 OI 与交易量改为三所聚合。

| 字段 | Binance | Bybit | OKX | 聚合方式 |
|------|---------|-------|-----|---------|
| 24h 交易量 | ✅ | ✅ | ✅ | **三所之和** |
| OI 现值 | ✅ 逐合约 | ✅ ticker 自带 `openInterestValue` | ✅ 全量接口 | **三所之和** |
| 价格 | ✅ 基准 | — | — | Binance 为准 |

**实测效果**（BTC）：
- 交易量：6.21B → **9.88B**（+59%）
- OI：6.76B → **12.79B**（+89%）

**诚实标注**：聚合覆盖 Binance+Bybit+OKX（永续 ~90% 量），不含 Gate/Hyperliquid/韩所现货；OI 分位/日线结构因子仍基于 Binance 单所（历史数据限制）。

## 五、核心评分逻辑（前导/工作台共用）

### 5.1 硬门槛五要素（全部通过才进池）

| # | 因子 | 条件 | 含义 |
|---|------|------|------|
| H1 | drawdown_60d | 距60天高点回撤 ≥40% | 深底 |
| H2 | range_20d | 近20日区间宽度 <30% | 横盘（非下跌中继） |
| H3 | vol_shrink_20d | 近5日均额 ≤60天峰额 20% | 量能枯竭 |
| H4 | near_low_20d | 收盘 > 近20日低点 ×1.03 | 不在创新低 |
| H5 | big_move_5d | 近5日无单日\|涨跌\|>15% | 无异常波动 |

**验证**：命中组合 5 天跌超 10% 概率 **3.3%** vs 全市场 **9.7%**——下行保护（跌得少），非预测暴涨。

### 5.2 强度分（基础 3 分 + 加分项，评分 ≥4 进候选池）

| 加分 | 条件 | 状态 |
|------|------|------|
| +1 | 回撤 ≥60%（深底） | ⚠️叙事 |
| +1 | 横盘 <20%（更横） | ⚠️叙事 |
| +1 | 缩量 <10%（更枯竭） | ⚠️叙事 |
| +1 | 近5日振幅 <8%（低波动） | ⚠️叙事 |
| **+2** | **OI 2M-8M（甜蜜区）** | ⚠️叙事 |
| **+1** | **OI 8M-30M（次甜蜜区）** | ⚠️叙事 |
| +1 | 大阳线后盘整（60d内 ≥15% 阳线+后20d盘整） | ⚠️叙事 |
| +1 | 缓涨（近10日 -5%~+15%） | ⚠️叙事 |
| +1 | Spring 测试（跌破前低后 5d 收回） | ⚠️叙事 |
| +1 | 正资费 >0.05%（套利者聚集） | ⚠️叙事 |
| +1 | 上线 ≤180 天（玩新不玩旧） | ⚠️叙事 |
| **-3** | 负费率 + 拉盘（控盘做空嫌疑） | ⚠️叙事 |
| **-3** | 额/OI ≥5（事件日，fwd5 -1.7% 强验证） | ✅验证 |

> **⚠️ 重要澄清**：OI 甜蜜区只是**加分项**，不是入围门槛。候选池对 OI 区间无硬限制——0-2M 的币（BEL/CRWD/TAIKO）靠结构分同样进池。实测 19 个候选分布：0-2M 7 个 / 2M-8M 7 个 / 8M-30M 5 个。

### 5.3 信号分类

```
评分 ≥ 4          → acc_candidate（蓄水候选）
额/OI ≥ 5         → avoid_event（回避）
评分 > 0          → watch（观察）
否则              → noise
```

### 5.4 OI 范围自定义控件（2026-08-08 新增）

- 前导筛选 + 筛币工作台各一套，纯**客户端过滤**（逻辑不变）
- 默认不设限 = 全市场；✓确定生效 + 状态显示"🔍 已过滤 OI XM ~ YM"
- 用途：想看"哪个 OI 区间的吸筹候选"由你决定

## 六、筛币工作台 L0-L5 完整流程

```
L0 环境闸门：BTC close vs SMA20
  ├─ 向上 → 候选池放行（验证：涨市 +0.8%/胜率56%）
  └─ 向下 → 候选降级 env_bear（验证：跌市 -5.3%/胜率31%）
      ↓
L1 候选池：吸筹结构评分 ≥4（硬门槛 + 强度分）
      ↓
L2 排除层（全部有验证或原文支撑）：
  ├─ ⛔ 事件回避：额/OI ≥5（fwd5 -1.7% 强验证）
  ├─ ⚠️ 薄盘口：深度 <200K（杀猪盘特征）
  ├─ ⛔ 大后期：OI>80M + 额/OI<3x + 跌幅>10%
  ├─ 📉 杀多：24h < -5%
  └─ ⛔ 负费率拉盘：负资费 + 价格涨
      ↓
L3 确认层（人工，不可自动化）：
  ├─ Wyckoff 结构（Spring/ST 手动看 K 线）
  ├─ 挤压三条件（高空头率 + 筹码分散 + 热钱）
  └─ 链上（控盘率/净流入/做市商）——P2 未接
      ↓
L4 告警（只对 watchlist 跑）：
  ├─ ST/Spring 出现（spring_test 规则）
  ├─ 大阳线后盘整（breakout_consolidation）
  ├─ 放量 + OI 跟上（额/OI≥5 + OI 24h>+2%）
  └─ 深负资费（<-0.05%）
      ↓
L5 执行（原则，非自动化）：
  ├─ 右侧优先（ST/Spring 确认后入场）
  ├─ 半凯利以下仓位
  ├─ 止损避开 Price Magnet
  └─ 候选池 = 10-20 币分散，单币 ≤2%
```

## 七、数据验证记录

### 7.1 验证 B：事件追高 = 负 EV（铁证）

| 分组 | n | 5天均值 | 胜率 | <-10% |
|------|---|---------|------|-------|
| 额/OI>5 全部事件 | 4592 | **-1.7%** | 40.5% | 27.9% |
| └ OI 跟上 | 2092 | -1.8% | 41.7% | 29.0% |
| └ 当日暴涨 | 2517 | -2.1% | 38.9% | 31.0% |

→ **额/OI 扫描器抓的从来不是"要涨的信号"，是"该跑的信号"。**

### 7.2 验证 A：吸筹结构 = 下行保护（多期 5×530 币）

| 分组 | n | 5天均值 | 胜率 | **<-10%** |
|------|---|---------|------|-----------|
| 全市场 | 2595 | -0.3% | 38.3% | **9.7%** |
| 底部回撤>40% | 195 | -0.5% | 34.9% | 5.6% |
| **+横盘+缩量+无新低（吸筹）** | 153 | -0.4% | 35.3% | **3.3%** |
| 吸筹+OI低位 | 87 | -1.5% | 33.3% | 6.9% |

**关键发现**：
1. 吸筹结构真实价值 = **下行保护**（dn10 9.7%→3.3%），不是预测拉升
2. **OI 低位叠加反而更差**（-1.5%）——OI 持续缩的币是资金在跑，不是建仓 → OI 分位降为展示
3. 环境分层：吸筹+低波动在 bear 里 dn10=0%，bull 里 3.7%

### 7.3 三个月验证结论表

| 方法论主张 | 判定 |
|-----------|------|
| 换手高只出现在暴涨/暴跌当天 | ✅ 证实 |
| 事件日追高 = 负 EV | ✅ 强证实（4592 事件） |
| OI 跟上 = 更健康 | ⚠️ 仅相对改善，仍为负 |

## 十一、诚实限制与提醒

1. **候选 ≠ 必涨**：彩票尾性质（HEI +428% 拉均值，中位数 +1.5%），小仓位分散，单币 ≤2%
2. **这是筛选器不是信号器**：入场时机（ST/Spring 确认、放量突破）需自己看 K 线
3. **环境条件性**：蓄水信号只有 BTC 向上时正期望（+0.8%/56%），向下 -5.3%/31%
4. **聚合覆盖三所**：不含 Gate/Hyperliquid/韩所现货；"Gate 定价权"和"韩所上币"维度未接入

## 十二·补、每日候选池归档（2026-08-11 新增）

**动机**：涨幅榜×候选池重合度调查中发现——线上 KV 的 `forward_data` 每 5 分钟被覆盖，**一周前的候选池无法回溯**，只能靠历史 kline 重建（口径有偏差）。因此给系统加上"每天自动记录筛出哪些币"的持久化能力，服务后续回测。

### 12·补.1 归档机制（worker 端，relay/评分零改动）

- **触发**：GitHub Actions 每 5 分钟 POST `/api/relay-forward` 时，worker 在写入 `forward_data` 的同时把当日 `signal == acc_candidate` 的币**合并**进 KV key `fwd_hist_YYYYMMDD`
- **日界**：**北京时间（UTC+8）**，北京 0 点自动切新 key，无需人工干预
- **记录内容**：每个候选币的 symbol / base_asset / forward_score / first_seen / last_seen（当日并集，重复推送只更新 last_seen 与最高分）
- **KV 成本**：每天 1 个 key（~3.5KB），每 5 分钟覆盖写回 ≈ 288 次/日；免费版配额 1000 次/日，总用量 ~720 次/日，余量 28%
- **存储**：KV 永久保留、容量无限（一年 ≈ 365 key ≈ 1.3MB），**与服务器内存/磁盘无关**
- 实现位置：`cf-worker/worker_v10_inline.mjs` 的 `hRWF`（归档）+ `hFH`（查询）

### 12·补.2 查询接口（2026-08-11 晚 → 深夜共 5 个）

```

# ⚡ 事件雷达：上榜 TopN 或单日涨幅 ≥big% 的事件（触发类型/候选关联/KPI）
GET /api/events?days=N&topn=M&big=X              # 默认 14/Top20/20%

# 📅 日榜回看：单日涨幅榜 + 候选标注（first_seen/lead_days/评分/入选价/埋伏收益）
```

### 12·补.10 🩹 涨幅榜归档静默失效 + 三层自愈（2026-08-13）

**故障现象**：用户发现"涨幅榜重合"过了 12 点仍未更新。线上 `overlap-stats` 显示 08-12/08-13 涨幅榜归档为空（`gainers: 0`），08-11 正常（20 条，seed 回填）。

**根因**：**字段名不匹配**。worker `hRL` 归档逻辑读 Binance 原始字段名（`priceChangePercent`/`quoteVolume`/`lastPrice`），但 relay.mjs 推送的是转换后的字段（`change_24h_pct`/`volume_24h_usdt`/`price`）。`isNaN(chg)` 恒为 true → 所有币被 `continue` 跳过 → 归档被空数组覆盖写回。**静默失败**：relay 推送正常（`Relay OK`），候选池归档正常（`fwd_hist` 用 `forward_score` 字段不受影响），只有涨幅榜归档悄悄变空。

**修复（三层，全部自动化）**：

1. **字段兼容（立即生效）**：relay.mjs 推送时同时带原始字段名（`priceChangePercent`/`quoteVolume`/`lastPrice`）→ 已推送 GitHub（commit `2e2a8b6`），VPS 每 15 分钟 git pull 自动同步；worker `hRL` 归档兼容两种字段名
2. **历史回填**：08-12 用 Binance 日线回填（680 币，`backfilled: true`）；08-13 由 worker scheduled 自愈回填（683 币，`healed: true`）
3. **自愈机制（以后不再出现）**：
   - **worker 侧**：scheduled 每 5 分钟检查当天归档为空 → 从 `exchange_proxy` 回填（30 分钟新鲜度守卫，防 relay 长期故障时用旧数据污染归档）
   - **relay 侧**：每次运行复用 forward 的 klineMap（100 天日线，**零额外抓取**），探测最近 3 天归档缺失 → 通过新接口 `/api/gainer-backfill` 回填（3 天窗口守卫，认证同 relay-tickers）
   - `hDG` 的 `total_archived` 修复为截断前真实数量（683 而非 topn 截断后的 20）

**验证结果**：
- 08-12：680 条 ✅（日线回填）
- 08-13：683 条 ✅（自愈回填 → 17:00 relay 实时覆盖，`healed` 标记清除）

- 全链路新鲜度：data/forward/coinfilter/demon 全部 17:00+ 更新

**部署记录**：worker `51ee16cb`（最终版，含 hGB + 自愈 + total_archived 修复）；relay commit `de9b1c7`（URL 修复）；回填脚本 `tools/_backfill_gainer_0812.py`（一次性，可重跑）。

**教训**：relay 推送字段与 worker 归档字段必须保持单一来源——本次是 relay 转换字段名后 worker 未同步。自愈机制（worker scheduled + relay 日线回填）确保即使再发生字段不匹配，归档也不会静默为空超过 15 分钟。
